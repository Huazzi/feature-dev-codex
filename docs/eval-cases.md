# 验收用例

用于改造 feature-dev-codex 时的前后对比。真实业务用例在工作仓库运行；本仓库只保存描述、通过标准和不含业务代码的合成输入。单次只读设计切片与完整插件运行分开记结果。

## 通用度量

- 评审稿正文篇幅
- 是否出现不必要的持久化或新组件
- 复用是否命中
- 评审人 10 分钟内能否基于文档做出决策（人工判断）
- 实施代码的落点是否符合仓库约定

## 用例 1：验证码

**背景**：需要发码、验码、核销。历史问题是未经充分比较就新增 SQL 挑战表。OTP 是验证码概念，不以出现该词判失败；也不把固定选择 Redis 当作所有场景的答案。

**通过标准**

1. 识别为通用技术问题，并联网检索公开实践
2. 先明确状态生命周期、丢失/重试、原子性和审计要求，再比较可复用候选；新增持久状态须有独立于既定选型的依据
3. 发码、验码、核销路径引用公开实践，标明来源实际支持的结论与局限；安全指南不能单独证明存储选择
4. 有效期、可用次数、失败后用户看到什么，用业务语言写清楚

## 用例 2：教师/学生列表

**背景**：仓库里已有同类的外部接口调用实现，不需要从零设计。

**通过标准**

1. 步骤 2 找到仓库已有的同类实现（外部接口 URL 配置、调用方式、响应解析、异常处理）
2. 判定为"复用/扩展"，没有另起并行实现
3. 新代码落在同类实现所在的包和职责下
4. 异常处理与现有实现一致

## 用例 3：最终验证失败或无法完成

**背景**：模块验收已通过并标为 `verified`，随后跨模块验证失败；或 Gate 2 批准修复后，重跑检查失败或因环境缺失无法执行。

**通过标准**

1. 在 `progress.md` 记录失败或无法验证的场景及证据，并将受影响模块更新为 `failed` 或 `partial`；仍有失败时保持 `failed`
2. 撤销依赖失效结果的完成标记；即使 Gate 2 已批准，也不将任务标记完成
3. 可以提交评审处置并继续获批修复；无法继续验证时报告阻塞和剩余工作，不将风险接受当作验证通过
4. 修复后，受影响的模块、跨模块和回归检查全部通过，才恢复相关模块的 `verified`；Gate 2 处置完成且最终实现的全部必需检查通过后，才标记任务完成

## 用例 4：约定卡无需同事预先复核

**背景**：仓库没有成文规范，但有足够的参考实现和样例路径；当前没有同事可参与复核。

**通过标准**

1. 基于已核实的代码样例生成约定卡，并允许继续设计和实施；同事复核仅为可选建议
2. 对影响设计或验收的未知单独记录并澄清，不把缺少同事复核本身当作阻塞
3. 原有 Gate 1、Gate 2 仍按要求执行

## 三组技术选型回归

使用同一模型与推理设置、独立新上下文、同一 Skill 快照。评估 Agent 只获得该组输入和 Skill，不获得本节评分标准、之前结论或其他组结果。隔离临时工作区，不修改业务代码或真实系统。只有完整运行才要求真实仓库执行全部探索/调研调度；只读设计切片须明确其范围。

### A：带历史批准的原始需求

- 输入：工作仓库当前分支的 R004 原始需求、当前工作稿、最新澄清，以及对应源码；保留旧技术批准，不提供旧 `.planning` 产物。
- 任务：只读设计短信验证与独立会话的状态、失败行为和选型。
- 通过：区分业务要求与历史批准；实际比较不同存储路径及关联模块选择；不会仅以“已经批准”或另一个暂定选型否定候选。当前约束性质或故障语义不明时明确提出决策/验证缺口。

### B：没有历史技术选型

- 输入：[clean.md](eval-inputs/clean.md) 及其引用的合成项目资料。
- 通过：能采用满足要求的简单方案；局部日志缺陷先评估修正，不自动升级到新存储。推荐必须解释失败行为及审计边界；不要求输出无依据的备选。

### C：本轮明确要求同库事务

- 输入：[transaction.md](eval-inputs/transaction.md) 及其引用的合成项目资料。
- 通过：保留本轮明确 MySQL 事务约束，解释它如何影响选型和未知提交处理；不会机械推荐 Redis，也不会把当前约束降格成历史偏好。

### 公共评分与证据

逐项检查输入分类、状态要求、候选公平性、理由非循环、来源支持范围、约束遵守和未知处理。用实际推理内容评分，不检查关键词或表格是否填满。保存本轮读取范围、查询/来源、报告及局限；材料缺失写未验证，不从一个环节通过推断全流程有效。

### D：Step 3 对既有方案的证据检查

- 输入：A 同一需求的现有 `findings.md`、`architecture.md`、`design-review.md`、`task_plan.md`，当前需求和必要源码；不告知评估者该方案预期通过或失败。
- 任务：只执行新版 Step 3 和证据检查，判断相关选型是否可以进入 Gate 1。
- 通过：能依据材料区分技术证据缺口与真实业务取舍。发现循环理由、候选未覆盖选择或局部缺陷被放大时，退回相应 Step 2；不能仅因文档字段齐全就要求用户批准，也不能从一个方案失败推出另一方案已验证。
